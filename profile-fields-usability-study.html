User Research · Usability Testing 2022

Customising Profile Fields Usability Study

UI Design Engineer · Hive Learning

A moderated usability study conducted to validate a new feature allowing organisation admins to manage their own profile fields. This was the first time Hive Learning had run structured usability testing, and the findings fed directly into fixes shipped before release.

Role & Scope

Test script writing
Participant recruitment
Remote session facilitation
Use case creation
Findings documentation
Accessibility review

Background

Hive Learning is a corporate e-learning platform used by organisations to run learning programmes for their teams. Each organisation has a set of profile fields that describe their users, things like job title, department, or location. Up until this point, any time an organisation needed to add, update or remove a profile field, someone at Hive Learning had to do it manually on their behalf.

Customising Profile Fields was a new feature designed to change that. It gave organisation admins a self-serve interface to manage their own fields without needing to raise a request. Admins could create new fields, choose the field type, set labels and placeholders, control visibility settings, and connect fields to third-party data providers like UKG Pro.

Before shipping, the team wanted to test whether admins could actually use it without running into problems. This was the study to find that out.

My Role

I was a UI Design Engineer at Hive Learning, sitting within the engineering team with a focus on UI and UX. This study was something I led end to end. I wrote the test scripts and prompts, recruited the participants, facilitated each session remotely, and documented the findings.

It was also the first time the team had run structured usability testing, so part of the work was establishing how to approach it and making the case for doing it at all.

Approach

I recruited five participants and ran each session remotely. The sessions were moderated, meaning I was present throughout and could observe where people hesitated, got confused, or took an unexpected path.

I structured the study around seven prompts, each corresponding to a key action an admin might need to take in the feature. Rather than asking participants what they thought of the interface, I gave them realistic tasks to complete and watched what happened. The goal was to see whether the feature worked in practice, not just whether it looked right.

The prompts covered navigating to the profile fields screen, adding a text field, adding a dropdown field with multiple options, editing an existing field, disabling a field from a data provider, finding help documentation, and adding a translation for a field.

Findings

Most tasks were completed without significant difficulty. The main interface was clear and participants generally knew where to go. The issues that came up were specific and fixable, which was a useful outcome in itself.

What worked well

Participants found the add field button easy to locate and self-explanatory. Navigating to the profile fields screen caused no real confusion. Editing an existing field was the quickest task in the whole study, with participants finding the manage button and completing the action with very little friction. The status banner on the modal, showing whether a field was currently enabled or disabled, was also noted as clear and useful.

Issues identified

The most significant usability issue was a bug in the dropdown field creation flow. When participants added a new dropdown option, the new option appeared behind a fixed element and couldn't be scrolled to. For the first three sessions, this meant participants couldn't complete the task at all. It was fixed before the fourth session.

The private and read only checkboxes caused confusion across multiple participants. Several ticked them without understanding what they did, and others skipped them entirely. When asked, one participant guessed that private would hide a field and read only would make it visible but not editable, which was a reasonable guess but not accurate enough to act on confidently. A tooltip or short description would have helped significantly here.

The label and value fields within dropdown options also caused uncertainty. Participants weren't sure what the difference was or which one would be visible to users.

Finding help documentation was the hardest task. Every participant struggled with it. There was no clear path to guidance from within the feature itself.

Accessibility gaps

One participant used a screen reader throughout the study. Their feedback surfaced a set of issues that wouldn't have been caught through standard testing. When the modal opened, focus didn't move to it automatically, meaning screen reader users had to navigate to it manually. There was no confirmation message when changes were saved, so there was no feedback that the action had worked. And closing the modal with the escape key wasn't supported, which is a standard expectation for keyboard users.

There was also no alt text or label on the data provider image, making it difficult to identify specific fields when navigating by screen reader.

Outcome

The findings were shared with the engineering team and the key issues were addressed before release. The scroll bug was resolved, modal focus was added so screen readers would land in the right place on open, and tooltips were introduced on the private and read only checkboxes to explain what each one did.

Beyond the specific fixes, the study changed how the team thought about testing. Having structured evidence of where users got stuck, including issues that had gone unnoticed during development, made the value of the process hard to argue with. It opened the door to usability testing becoming a more regular part of how the team worked.

What I Learned

01

Watching someone use something tells you far more than asking them what they think of it. Several issues in this study only surfaced because I could see participants hesitate or take a wrong turn, not because they flagged a problem directly.

02

Including a screen reader user changed the quality of the findings significantly. The accessibility gaps that came up were real issues that affected usability for those users, and they wouldn't have been caught any other way.

03

Terminology that feels obvious to the team building something can be completely opaque to the people using it. Private, read only, label, value; none of these caused confusion internally, but participants struggled with all of them.

04

Getting findings in front of engineers with clear, observed evidence made it easier to prioritise fixes. It shifted the conversation from opinion to fact.
